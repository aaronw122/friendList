# Friend List — R1 Review Verdict (Judge)

Inputs: PLAN.md · r1-consolidated (prosecution) · r1-challenge (defense).
Severity bar: "the app still delivers its core promise correctly" (friend-sent songs auto-added, privately, set-and-forget). Silent non-function is severe.

## Per-issue verdicts

C1: UPHELD (Critical) - TCC FDA is keyed per-executable code identity; the plan runs all chat.db reads in a separate nested `friendlist-agent` binary, so the app-level grant does not reliably cover it. Failure mode is total, silent non-function of the "seeing" leg. The plan's own Risks bullet acknowledges the uncertainty but the architecture still commits to it, and the fallback ("guide granting it explicitly") means asking users to hunt down a headless helper binary in Full Disk Access settings — not viable onboarding. Both sides agree; the single-executable fix (SMAppService.mainApp login item, poll in the app process) is the correct resolution and also moots M1/Med2 and part of M2.

C2: UPHELD (Critical) - Plan commits to "One Spotify developer app backs all installs" (Components 5) *and* public web distribution (M5/Distribution). Spotify dev-mode apps have a hard low per-client_id user cap (defense verified 5 as of Mar 2026; even the plan's own ~25 figure is fatal), and extended quota requires a registered business at large MAU scale. A shared embedded client_id and "download it from the web" cannot coexist. The Risks section defers the decision to M5, but the committed architecture is non-viable for the stated product; re-architect now to BYO-client_id (or explicitly scope to personal/allow-listed use). Both sides agree.

M1: DOWNGRADED (Medium) - The prosecution overstates ("two writers to same data" is not in the plan), but the defense's "distinct files" partition is also not in the plan — Component 9 says settings are "persisted to the state container" and Component 8 offers "JSON/Codable or a small SQLite" with a single-writer guard that only covers duplicate agent launches. Two processes genuinely write into an undefined container layout; the fix is one paragraph (explicit per-file ownership: agent owns runtime state, app owns settings) and the whole issue is moot under C1's single-executable fix. Spec-clarity gap, not a committed defect.

M2: UPHELD (Must-fix) - Verified platform fact: Spotify PKCE refresh tokens are single-use and rotate on every refresh. The plan says only "store the refresh token in Keychain… silent access-token refresh" and has *two* processes (app + agent) reading the same Keychain item. Without (a) atomic persistence of the rotated token on every refresh and (b) a single designated refresh owner, auth silently dies — adds stop forever with no error, the exact silent-non-function the severity bar names. The single-use persistence requirement bites even a lone writer, so C1's fix does not moot this. Both sides agree.

M3: DISMISSED - Misread by the prosecution. The plan states "the **only** thing that holds the watermark is an add that failed *before* its URI reached the durable retry queue" — "holds" means the watermark cannot advance past that message, which is exactly the finding's proposed fix ("stop at the first unresolved message"). Advancement is contiguous by construction; no adds are dropped. At most add one clarifying sentence ("watermark = highest ROWID below which all messages are terminally resolved"), but there is no defect.

M4: DISMISSED - Subsumed by C2. The plan collects no email anywhere; the allowlist obligation only exists on the shared-client_id + dev-mode + public-distribution path, which C2's verdict already kills. Under either C2 resolution (BYO-client_id or personal-only) no allowlist and no email exist. Not an independent defect; fold into C2's fix as "state that no shared allowlist exists."

M5: DOWNGRADED (Low, merge with L4) - The grant path is fully specified (probe read, explainer, deep link, poll). Permanent denial cannot be "skipped" because the app genuinely cannot function without FDA, and the user is *present at the screen* — this is not silent background failure, so the severity bar is not met. What's missing is stuck-state copy ("still waiting / open Settings again / can't continue without this"), which L4 already captures. One caveat inherited from M8: if grant detection requires an app restart, the poll can hang even after a successful grant — see M8.

M6: UPHELD (Must-fix) - The defense's DISPROVEN is overreach. The menubar item exists, but the plan specifies its contents as "status, pause/resume, open playlist, quit" — no error or attention state is defined anywhere, and no mechanism for the headless agent to signal the UI. A revoked/expired/lost refresh token (which M2 shows is *easy* to hit, not a rare edge — one unpersisted rotation kills auth) produces indefinite silent non-function: songs quietly stop being added and nothing ever tells the user. That is precisely the severity bar's "silent non-function," and it compounds M2. Required: a defined error/attention state (e.g. menubar badge + "Reconnect Spotify" prompt) and the agent→UI signaling path.

M7: DOWNGRADED (Low) - The prosecution dropped the plan's caveat: §Privacy says "never message content or contact identifiers *beyond what filtering needs locally*," which covers `allowed_chats`/`allowed_handles`. The one true residue is the retry queue persisting source chat + sender — identifiers not needed for filtering — a literal mismatch with the sentence but local-only, so the privacy *pillar* (nothing leaves the Mac) is intact. Fix in one line: drop the fields from the retry queue or amend the sentence.

M8: DOWNGRADED (Medium) - Both sides are partly wrong. The defense is right that macOS doesn't *force* a relaunch (System Settings offers optional "Quit & Reopen"), but wrong to wave it off: for many apps (Terminal is the canonical case) an FDA grant does not take effect in the already-running process, so the plan's poll-for-access can hang *after* the user has granted — a broken-feeling onboarding moment. Worst-case recovery is benign (relaunch replays two pre-auth screens; no state or auth exists yet), so this is not Must-fix, but the design must (a) validate at M3 whether a live probe sees the grant without relaunch, and (b) if not, show "Quit & Reopen" guidance and persist the onboarding step so relaunch resumes at Scope.

## Holistic Assessment

Surviving set: C1 (Critical), C2 (Critical), M2 (Must-fix), M6 (Must-fix), plus Medium M1/M8 and Low M5/M7.

If the upheld issues co-occur, the app does **not** deliver its core promise — each Critical/Must-fix breaks a different leg of it:

- **C1** breaks the *seeing*: the agent's chat.db reads are denied and no song is ever detected — silently.
- **C2** breaks the *"download it"* distribution: at most a handful of users can ever authenticate against the shared client_id.
- **M2** breaks the *set-and-forget* longevity: one lost token rotation and auth dies — silently.
- **M6** guarantees the silences stay silent: when M2 (or any auth death) fires, no surface ever tells the user, so the failure persists indefinitely.

M2+M6 deserve explicit escalation as a *pair*: M2 makes silent auth death probable (not a rare edge), and M6 removes the only chance of the user noticing. Together they convert a recoverable auth hiccup into permanent, invisible product death — treat them as one work item (single refresh owner + atomic rotated-token persistence + a defined "Reconnect Spotify" attention state).

The mitigating fact — argued by the defense and confirmed against the plan — is that all four survivors are already named in the plan's own Risks section, and each has a known, architecture-compatible fix: single executable (C1, also mooting M1 and the keychain-sharing half of M2's race), BYO-client_id or explicit personal-only scope (C2, mooting M4), single-owner atomic token persistence (M2), and a menubar attention state (M6). None invalidates the product shape. **Verdict on the plan: sound concept, correct feasibility analysis, but not implementable as written — the four upheld items are prerequisites, not polish. Apply the four fixes (ideally before M1/M2 milestones, since C1 changes the process architecture and C2 changes onboarding) and the core promise holds.**
