## Critical
- **`SMAppService.agent().register()` with `Program` = the app's own executable is documented to immediately launch a SECOND instance of the app, and the plan has no single-instance/handoff design.** (§Onboarding 4; §Architecture lines 76-78; §Components 1 & 2; §Tech stack) Apple DevForums #745712 confirms this exact pattern: `register()` activates the job right away (RunAtLoad) instead of adopting the already-running app, so at onboarding "Done" you get the LaunchServices-launched onboarding instance AND a launchd-launched instance running the same menubar simultaneously — and again on every subsequent manual launch. The `flock` "guard" is the only thing preventing double-writes, and the plan never says which instance wins or how the loser exits. **Fix:** define the single-instance contract explicitly — the onboarding instance registers the agent but sets it to start at *next* login (or, on detecting an already-running instance, the launchd instance exits 0 and the running instance stays as the live one); lock-loser must exit cleanly, never double-write. Consider documenting the alternative (`SMAppService.loginItem` for launch-at-login + an in-process crash-relaunch strategy) if the dup-instance handoff proves fragile.

## Must-fix
- **`KeepAlive = true` (boolean) defeats the menubar "Quit" and turns any clean exit into a ~10s respawn storm.** (§Architecture line 77; §Components 1 line 79, Component 2 line 111; §Tech stack line 212) With boolean KeepAlive, launchd relaunches the process regardless of exit code, so the user-facing "quit" command (and the lock-loser exit from the Critical above) triggers immediate relaunch — the app becomes un-quittable and a manually-opened 2nd instance that self-quits churns respawns. **Fix:** specify `KeepAlive` as a dict `{ SuccessfulExit: false }` (restart on crash only) so RunAtLoad still gives login-start + crash-restart while a clean Quit stays quit; have "Quit" additionally `unregister()` (or offer "Pause" as in-app state, "Quit" as full teardown).
- **Onboarding + M2 still omit the mandatory Spotify "Users and Access" (User Management) allowlist step; auth fails for the owner without it.** (§Onboarding 3; §Components 5 line 141; §M2) Grounded in Spotify's Quota Modes docs and the Feb 2026 policy: a dev-mode app can authorize at most **5** users and *each* authorizing account — **including the owner's own account** — must be added under Users and Access before it can authenticate; otherwise `ASWebAuthenticationSession` returns "user not registered." The plan explicitly (and now incorrectly) says "no allowlist." **Fix:** add an onboarding sub-step "add your own Spotify account under Users and Access" with the exact dashboard path, and make M2/M3 acceptance require completing auth as a freshly-allowlisted account (not a pre-existing session).

## Medium
- **launchd-exec breaks LaunchServices' single-instance protection, so re-opening FriendList.app silently does nothing.** (§Components 2 line 113; contradicts R2 Impl-note) Because the live instance was exec'd directly by launchd (not via LaunchServices), double-clicking the app in /Applications spawns a new instance that self-quits on the `flock` — the user sees "nothing happened" when trying to reach Settings. **Fix:** on second launch, detect the existing instance and `NSApp.activate`/surface the menubar or Settings window instead of silently quitting; update the plan text to mark the `flock` guard as load-bearing (no longer "redundant with LaunchServices").

## Low
- **Premium is now a HARD requirement, not "may be required."** (§Onboarding 1 line 45; §Components 5 line 141; §Risks line 267) Spotify's Feb 2026 change makes a Premium owner account mandatory for dev-mode function, which invalidates R2's "drop Premium" suggestion. **Fix:** change Welcome's hedged "a Premium account may be required" to a firm "requires Spotify Premium," consistent with the other sections.

## Impl-note
- LaunchAgent plist must reference the **executable** path (`Contents/MacOS/FriendList`), not the `.app` bundle, and live in `Contents/Library/LaunchAgents/` with `Label` matching the `plistName` passed to `SMAppService.agent(plistName:)` (DevForums #750528). Prefer a bundle-relative reference so it resolves after the /Applications move. Caught immediately when authoring the plist.
- Dev-mode test-user cap is now **5** (was 25 in R2); if plan copy ever states a number, update it.
- attributedBody: `NSUnarchiver` is deprecated/unavailable in Swift for typedstream blobs (§Components 3) — use `NSAttributedString(data:documentAttributes:)` (streamtyped) or a typedstream parser with the byte-scan `https://…spotify` fallback (carryover).
