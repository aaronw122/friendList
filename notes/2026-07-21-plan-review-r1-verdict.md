# Round 1 Verdict — Referee

Verified independently against `PLAN.md`. Both parties' positions read.

## Per-issue verdicts

- C1: UPHELD (Critical) - Plan §2 explicitly specifies `immutable=1` on a live WAL database; immutable mode ignores the `-wal` sidecar and disables change detection, so uncheckpointed (i.e., recent) messages are invisible — and reading a file that mutates under an immutable assumption risks corrupt reads. Defeats the core poll loop; both parties agree and the concession is sound.
- C2: UPHELD (Critical) - Architecture and §5 show unconditional `add → persist last_seen ROWID` with no success gate or retry queue anywhere in the plan; a routine 401/429/5xx on add permanently and silently drops that song. impl_notes acknowledgment is not a resolution, and M3 acceptance never tests mid-run add failure. Silent data loss = severe per the standard.
- C3: UPHELD (Critical) - The plan defines `last_seen` persistence but never its bootstrap value; the natural default (0) against `WHERE ROWID > :last_seen` scans full history and mass-mutates a live playlist on first launch. Undefined state with a destructive default is exactly a plan-level defect; elevation from Must-fix was justified.
- M1: UPHELD (Must-fix) - §4 scope list omits `playlist-read-private`. The opt-in all-playlists scan via `GET /v1/me/playlists` unambiguously omits private playlists without it, and the documented contract for reading a private playlist's tracks requires it; even where the API is leniently permissive for owner-by-ID reads, a plan relying on undocumented leniency for its dedup backstop is defective. Failure mode is silent duplicate adds. Stays Must-fix (not Critical): Liked-Songs dedup and the local seen-set still function, and the fix is one token.
- M2: DISMISSED - §4 already assigns "Authorization Code + PKCE, one-time browser login" to `spotify.py` and Setup names the loopback redirect URI; the listener is an ordinary implementation detail inside that stated responsibility. Cannot produce wrong output — auth either completes or fails loudly at setup. Defense is correct.
- M3: DOWNGRADED (Low) - `client_id`/`redirect_uri` must live somewhere and the plan doesn't say where, but this cannot fail silently: nothing runs until the implementer wires it, so it surfaces loudly at build time. Worth a one-line home (config or constant), not a Must-fix.
- M4: DOWNGRADED (Low) - The split-commit claim (row inserted, `attributedBody` written in a later transaction) is asserted, not demonstrated; SQLite readers see committed transactions atomically, and the known late-write on link messages is the preview `payload_data`, not the body. Plan already gates attributedBody behavior on M1 validation against real data. Keep as an M1 verification note (and C2's fix — don't advance watermark past unprocessed rows — covers the residual risk).
- M5: DISMISSED - The plan's own words are "scan every **owned** playlist"; filtering `/me/playlists` by `owner.id` (via `GET /v1/me`) is the trivial, faithful implementation of stated intent, not a missing decision. Feature is opt-in and default off. Defense is correct.

## Holistic Assessment

The dismissed/downgraded items (M2, M3, M4, M5) do not compound: M2/M3 are build-time-loud auth wiring that cannot silently misbehave, M4 is unproven and covered by both the M1 validation gate and the C2 fix, and M5 is an off-by-default feature whose intent the plan already states correctly. Even co-occurring, they leave the feature producing correct output. No escalation of the downgrades is warranted.

The upheld set, however, is jointly fatal as written: on day one the daemon floods the playlist with all historical links (C3) while private-playlist dedup silently fails and re-adds duplicates (M1), then goes blind to new messages (C1), and silently drops any song whose add hits a transient failure (C2). The prosecution's core case stands: **the plan is not implementable as written until C1, C2, C3, and M1 are fixed.** All four fixes are small and localized (drop `immutable=1` + fresh per-poll `mode=ro` connection; gate watermark advance on add success with a durable pending queue; bootstrap `last_seen = MAX(ROWID)`; add `playlist-read-private`), after which the plan's architecture is sound.
